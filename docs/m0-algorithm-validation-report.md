## 2. 缺陷 1：F5 高风险清单的合并粒度错了

### 现象

v1 按 100m 分段逐段合并，产出 15 个窗口，全是这种：

```
07:00:26–07:00:32  东华门路  58m
07:00:39–07:00:58  东华门路  93m
07:01:08–07:01:15  东华门大街  88m
```

**时间窗全落在同一分钟。** 100m @ 53km/h = **6.8 秒**。

### 根因

**合并粒度 = 分段粒度。** 分段是为了计算精度选的（100m），却直接拿去当展示单元了。PRD F5 明确要求「相邻同等级路段自动合并，避免碎成一堆 100m 条目」—— 我违背了自己写的需求。

### 修正

**按道路名（导航语义单元）聚合，再合并相邻同名窗口。**

导航语义下，「东长安街 07:02–07:05」才是一个有意义的风险单元；「第 1234 段」不是。用户看的是路名，不是段号。

### 效果

```
v1 逐段合并 -> 15 个窗口
v2 按道路名合并 -> 3 个窗口

  【高】东长安街    |  07:02–07:05 CST  |  约 1.8 km  |  峰值 67 分
  【高】东华门路    |  07:00–07:00 CST  |  约 0.4 km  |  峰值 67 分
  【高】东华门大街  |  07:01–07:01 CST  |  约 0.1 km  |  峰值 64 分
```

第二行「东华门路 07:00–07:00」仍不可读 —— 剩下这一个是因为该路段本身只有 400m，且高风险的窗口确实不足一分钟。

> **待定问题**：清单应展示「路段」还是「时间窗」为主？若用户关心的是「我几点会难受」，则应以**时间窗**为主键组织清单，而非路名。这需要产品决策。

## 3. 缺陷 2：F6「建议出发时间」的指标是错的（概念性）

### 现象

用 PRD F6 原定的指标（平均暴露度）扫描全天：

```
 出发   平均暴露  P80峰值  高以上段数
 05:00     5.40     47.8      0
 07:00     7.80     67.2     55
 11:00     1.44      5.5      0
 16:00     2.31     99.5      9
 19:00     0.00      0.0      0   <- 平均最优
```

**「最优」= 19:00 出发** —— 太阳已落山，无逆光。数学上正确，产品上毫无价值。

### 根因（两层）

**第一层：关于这条路线**

路线朝向分布：

```
  东  ( 90°)  47.3 km  34.1%
  东南(135°)  70.6 km  50.9%     <- 东西向合计 85%
  南  (180°)   9.1 km   6.5%
  西  (270°)   3.1 km   2.3%     <- 只有 3.1 km
  西北(315°)   1.8 km   1.3%
  其他          6.6 km   5.0%
```

**只有 3.1 km 的西向路段**，但它在 18:16 正好迎上落日（太阳高度角 **0.5°**，离轴角 **0.3°**，峰值 **99.5 分**）。

平均暴露度把这个致命点 ÷ 138km 全长，稀释掉了。

**第二层：这是更普遍的问题**

即使换了更好的指标，只要搜索窗口覆盖全天，优化器总能找到「夜间出发」来把风险压到 0。这不是路线的问题，**是指标定义域的问题**。

### 修正方案

**(a) 主指标改为双指标**

```
Cost(t) = 峰值风险 R_max(t)              <- 主排序键
Constraints: 到达时间落在用户可接受窗口内   <- 硬约束，而非软惩罚
Secondary:   高以上里程占比
```

**不要用平均暴露度做主指标** —— 它系统性地低估「局部致命」的情况。

**(b) 必须报告「峰值下界」**

即**无论何时出发都躲不掉的最坏峰值**。这是路线自身几何决定的，与出发时间无关。

**(c) 当峰值下界 ≥ 60 时，输出「无法完全避开」的结论**

这对应 PRD F6 的「反建议」要求与验收用例 T07。**对这条北京→天津路线，早晚各有一个不可回避的峰值**：

- 早晨向东：太阳在正东，东向路段（47.3km）迎面
- 傍晚向西：太阳在正西，西向路段（3.1km）迎面

### 一个重要的统计性发现

```
16:00 出发 -> P80 峰值 99.5   (9 段 >= 60 分)
```

**P80 聚合会抹平瞬时峰值。** 因为 P80 是对「该 100m 路段通过时间窗内的多个采样点」取分位数：

- 100m @ 53km/h = 6.8 秒，而采样步长 5 分钟 → 该段只有 1–2 个采样点
- 对于更长的段，P80 会把「1 分钟的极端逆光」在「5 分钟的正常」中稀释

**这意味着**：

| 量 | 性质 |
| --- | --- |
| 路段级 P80 风险 | **可以通过改出发时间规避**（优化器能压低它） |
| 瞬时级峰值风险 | **可能无法规避**（太阳就在那个方位） |

所以「建议出发时间」功能的天花板是：**能把路段级风险压下去，但压不掉瞬时峰值**。产品文案必须诚实反映这一点，不能说「换个时间就没问题了」。

## 3.5 🆕 峰值风险曲线是**不连续**的（本次最重要发现）

在按 Q10 决策（用户选「到达时段」）设计实现时，做了一次 5 分钟精扫，结果**推翻了「15 分钟步长够用」的假设**。

### 实测曲线（15:00 – 17:30，5 分钟步长）

```
   出发     峰值R    峰值道路      通过时太阳高度角
   15:40     98.3   昆仑路          0.91°
   15:45    100.0   昆仑路          0.04°   ← 死正对
   15:50     91.0   徐庄子匝道桥     2.55°
   15:55     95.5   金钟桥          1.43°
   16:00     99.5   金钟桥          0.46°
   16:05     23.2   分钟寺桥        23.05°   ← 断崖，跳变 76.3 分
   16:10     24.4   分钟寺桥        22.15°
```

**注意峰值所在的道路都换了**：15:45 之前是「昆仑路」，16:05 之后变成「分钟寺桥」。说明**致命点从落日路段转移到了别的路段**。

### 机理

那段致命的西向路在**里程约 120km 处**，行程需约 **136 分钟**。

```
出发 15:45  →  18:18 通过该路段  →  太阳高度角 0.04°、离轴角 0.00°  →  峰值 100.0
出发 16:05  →  18:38 通过该路段  →  太阳已落山（高度角 < 0）        →  该路段风险归零
```

**只有 15:45–16:00 出发，才会恰好在 18:16–18:18 通过它。**

### 后果：搜索步长必须分级

| 事实 | 数值 |
| --- | --- |
| 15:00–17:30 内峰值 ≥ 60 的出发时刻 | **15 个**（5 分钟粒度） |
| 15 分钟步长能覆盖到的 | **2 个** |
| **漏掉** | **13 个** |

**15 分钟单步长扫描会漏掉 87% 的高危窗口**，且可能在尖峰边缘给出建议。这直接否定了 PRD F6 原定的「15 分钟步长」设计。

### 修正后的搜索策略

| 阶段 | 步长 | 目的 |
| --- | --- | --- |
| ① 全局粗扫 | 15 分钟 | 覆盖全天，定位候选区域 |
| ② 局部精扫 | 5 分钟 | 在最优解附近**以及所有等级跃迁边界**附近细化 |

### 更重要的：正确建议的形态变了

实测数据表明，正确的产品输出**不是**「推荐一个出发时间」，而是**给出危险边界**：

> **16:05 之后出发，可完全避开该落日路段。16:00 出发则会在 18:16 正对太阳（离轴角 0.35°，峰值 99.5）。**

这比「推荐 16:15 出发」信息量更大、更可执行 —— 用户理解的是「有一条线不能越」，而不是「一个魔法时刻」。

**已写入 PRD F6**：新增「危险出发窗口 / 安全出发窗口」输出项，以及「最优解距离危险窗口 < 15 分钟时必须警告」的规则。

### 性能实测

| 项 | 数值 |
| --- | --- |
| 单次全路线仿真（200m 分段、5min 采样） | **20 ms**（Python） |
| 全天 15 分钟粗扫（96 次） | 2.0 s |
| 全天 5 分钟扫描（288 次） | 5.9 s —— 略超 PRD 的 5 秒预算 |

> Python 原型 5.9s，TypeScript 实现应更快（3–5×）。配合两阶段搜索（粗扫 96 次 + 局部精扫约 60 次 ≈ 156 次）约 **3.1 s**，在预算内。若仍超出，用 Web Worker + 分段缓存。

## 4. 场景核验：结果是否符合驾驶直觉？

这是整份报告最实用的一节 —— 用真实数据检查算法输出是否「像人话」。

| 场景 | 算法输出 | 直觉判断 |
| --- | --- | --- |
| **清晨 07:00 出发朝东** | 东长安街，朝向 84°，峰值 **67.2（高）**<br>时刻 07:02:37，太阳方位 83.3°，高度角 7.7°，**离轴角 0.4°** | ✅ **完全正确**。日出后 45 分钟，太阳在正东偏南、高度 7.7°，向东开就是正对太阳。离轴角 0.4° 说明几乎死正 |
| **下午 16:00 出发朝西** | 金钟桥，朝向 270°，峰值 **99.5（极高）**<br>时刻 18:16:04，太阳方位 270.3°，高度角 **0.5°**，离轴角 **0.3°** | ✅ **完全正确**。落日贴地平线正对车头，这是最危险的情况 —— 遮阳板完全无效 |
| **正午 12:00 出发** | 宾馆西路，朝向 315°，峰值 8.2（低）<br>太阳高度角 39.8°，离轴角 2.1° | ✅ **正确**。正午太阳高挂，即使方位对齐也是从上方来，遮阳板可挡 |

**三个场景全部符合驾驶直觉，且离轴角数值解释了「为什么危险」。**

特别是 16:00 那一条：**太阳高度角 0.5°、离轴角 0.3°、峰值 99.5** —— 这是产品价值最集中的场景，也是通用导航完全给不出的信息。

## 6. M0 阶段结论

**算法核心站得住。** 太阳位置、离轴角、风险分数三项在真实数据上全部验证通过，输出符合驾驶直觉。

**M0 期间共发现并修正 3 个设计缺陷**：

| # | 缺陷 | 性质 | 修正 |
| --- | --- | --- | --- |
| 1 | F5 合并粒度 = 分段粒度 | 实现细节 | 改为按路名聚合 |
| 2 | F6 用平均暴露度 | **概念性** | 改为峰值风险 + 到达时段硬约束 |
| 3 | F6 单步长 15min | **概念性** | 两阶段搜索；新增危险边界输出 |

> 缺陷 2 和 3 都是**在被写进代码之前就发现的产品设计问题**。这正是 M0「先用真实数据验证算法与产品假设」的价值 —— 如果直接进 M1 写 UI，这两个缺陷会被固化成实现，之后返工成本高得多。

**Q9 / Q10 已定稿，F5 与 F6 的设计可以进入实现。**

**下一步（M1）**：搭 TypeScript 工程，把已验证的算法移植为纯函数模块，并实现 `AmapProvider`（实现要点见 [amap-provider-findings.md](amap-provider-findings.md) §6）。
