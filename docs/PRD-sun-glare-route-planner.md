## 1. 产品概述

### 1.1 一句话定义

一个**出行前的路线预演工具**：用户输入起点、终点和出发时间，产品沿着整条路线逐段计算「太阳是否会正对车头照进眼睛」，在地图上把刺眼路段标出来，并给出每段的出现时间窗与建议出发时间。

### 1.2 要解决的问题

清晨日出后约 1 小时、以及傍晚日落前约 1 小时，太阳高度角低、方位角接近地平线。此时若太阳正好位于车辆前进方向，会出现以下后果：

| 后果 | 具体表现 |
| --- | --- |
| **瞬时致盲** | 风挡玻璃与仪表台反光叠加，视线内出现大面积光斑，看不清前方 50–100m |
| **距离误判** | 无法准确判断前车距离和刹车灯状态，追尾风险显著上升 |
| **无法用遮阳板破解** | 遮阳板只挡上方直射光，当太阳贴近地平线时基本无效 |
| **隧道出口 / 桥面突变** | 长隧道出来瞬间遇到正对太阳，瞳孔来不及适应，是最危险的一类场景 |

现有导航产品（高德、百度、Google Maps）解决的是「怎么走最快」，**没有任何一家在出发前告诉用户「你这一路会不会被太阳糊脸」**。这是一个真实存在但被完全忽略的痛点。

### 1.3 目标用户

| 用户类型 | 场景 | 核心诉求 |
| --- | --- | --- |
| **P0 长途自驾司机** | 春节/国庆返乡、跨省 500km+ | 想知道哪几段要戴墨镜、能不能换个时间出发 |
| **P0 职业司机** | 网约车、货车、客车 | 每天固定路线，想提前知道今天几点会难受 |
| **P1 摩托车 / 骑行爱好者** | 头盔面罩无遮挡，逆光影响更直接 | 同上，但对阈值更敏感 |
| **P2 普通通勤族** | 早晚高峰固定方向（如向东上班） | 想知道「今天要不要早点走 20 分钟」 |

### 1.4 产品边界（一句话）

**本产品是出发前的「风险预览」工具，不是驾驶中使用的导航，也不替代任何安全驾驶判断。**

### 1.5 不做什么（明确排除）

以下内容**不在 MVP 范围内**，且部分为「永不做」：

| 项 | 原因 |
| --- | --- |
| 实时导航、语音播报、转向提示 | 涉及驾驶中交互，安全责任与合规成本极高；本期定位为出发前工具 |
| 自动驾驶 / 辅助驾驶联动 | 不涉及车辆控制，纯信息产品 |
| 遮挡物精确建模（建筑、树林） | 需要 3D 建筑与植被数据，成本远超收益，列入远期 |
| 太阳眩光的医学 / 法律结论 | 本产品输出的是**工程估算**，不构成安全承诺（见第 9 章免责） |
| 路线本身的最优性 | 本产品不替代导航，路线来源可复用用户已有习惯 |

## 2. 用户故事与典型场景

### 2.1 典型场景走查

**场景 A：春节返乡，早上出发（最高频）**

> 张先生要从上海开车回合肥，约 470km。他原计划 10 月 3 日 07:00 出发。使用本产品后发现：G42 沪蓉高速 K120–K180 段在 07:20–08:10 期间太阳方位角与行驶方向夹角小于 20°，属高风险；若推迟到 08:30 出发，该段风险降为低。他据此改了出发时间。

**场景 B：傍晚回程，正对落日**

> 李女士下午 17:30 从郊区返回市区，全程向西。产品提示 18:05–18:40 全路段为高风险，且此时段无可行绕行方案，建议她提前到 16:30 出发，或准备好偏光墨镜。

**场景 C：山区隧道群（高价值差异化场景）**

> 王先生走山区高速，连续 6 个隧道。产品提示第 4 个隧道出口方向正对 08:00 的太阳，出洞瞬间即为高风险。这类提示是通用导航完全给不出的。

**场景 D：职业司机日常路线**

> 一位每天固定跑同一条路的货车司机，保存了路线，每天早上打开看一眼「今天几点会逆光」。

**场景 E：反直觉场景（负向案例，用于验证不过度报警）**

> 用户向北行驶，太阳在东南方。夹角约 135°，产品应明确显示「全程无逆光风险」。**如果此时报警，产品就失去了可信度。**

## 3. 需求边界与关键约束

### 3.1 范围三档

| 档位 | 内容 |
| --- | --- |
| **MVP v1.0 必做** | 起终点输入、出发时间选择、路线获取、逐段逆光风险计算、风险分级着色、高风险路段清单 + 时间窗、建议出发时间、无风险时的明确提示 |
| **v1.1 迭代** | 天气叠加（云量/降水降级）、常用路线收藏、计算依据展示面板、多出发时间对比 |
| **v2.0 远期** | 反向/返程计算、途经点与过夜拆分、遮挡估算（地形 DEM）、移动端离线缓存 |

### 3.2 关键约束（必须在设计中正视）

| # | 约束 | 影响 | 应对 |
| --- | --- | --- | --- |
| C1 | **OSM 中国路网精度不足**：测绘法规限制导致高速匝道、新通车路段、车道几何缺失或整体偏移 | 路段朝向计算错误，直接导致误报/漏报 | 采用**双层数据源架构**（见 8.2），OSM 作为零成本基线，预留高德/百度适配层；UI 上标注数据来源与置信度 |
| C2 | **无高程数据 → 无法算坡度** | 上下坡时太阳相对车头的真实高度角有偏差，山区误差放大 | MVP 假设路段水平；用 SRTM 90m 免费高程做 v1.1 增强（见 6.3.4） |
| C3 | **不做遮挡建模** | 山体、树林、建筑挡光时仍会报警（假阳性） | 定位为「上界估算」：**实际风险只会 ≤ 显示风险**，在免责说明中讲清 |
| C4 | **坐标系不一致**：OSM 用 WGS-84，高德用 GCJ-02，两者位置偏移约 **710m**（实测） | 底图与路线错位，路线「飘在路外」 | **已实测澄清**：偏移对 **bearing 计算无实质影响（最大 0.25°）**，因为求差时常数偏移被消掉。但**地图渲染必须与底图坐标系一致**。规则：用高德底图则全链路保持 GCJ-02，零转换（详见 [amap-provider-findings.md](amap-provider-findings.md) §4） |
| C5 | **时区与真太阳时**：中国全境用 UTC+8，但新疆等地「北京时间 08:00」实际太阳高度很低 | 若只按本地时间直觉判断会错 | 一律使用 **IANA 时区 + 精确太阳位置算法**，不依赖用户的本地时间直觉 |
| C6 | **公共路由服务的限流** | 演示或小规模可用，量一大就断 | MVP 用高德 Key（有配额兜底）+ 前端缓存；上量后评估提额或自建 |
| C7 | **驾驶中使用风险** | 边开车边看 = 危险 | 明确定位为出发前工具；页面不做驾驶中适配，必要时在首页提示「请勿在驾驶中操作」 |
| C8 | **`orientation` 字段不可用**（实测）：高德返回的 `orientation` 只有 8 档（45° 分辨率），且每个 step 仅一个值，一个 97.7km 的高速段也只给一个「东南」 | 若误用它算离轴角，量化误差 ±22.5° **大于信号本身**（`w_angle` 在 15° 处已降到 0.5），会导致结果完全不可信 | **必须从 `polyline` 自算 bearing**（大圆方位角公式）。`orientation` 仅可用于 UI 粗略文字描述。详见 [amap-provider-findings.md](amap-provider-findings.md) §3.1 |
| C9 | **坐标系与地理合规**：高德 Key 的认证主体边界 | 个人认证不得用于商用，否则个人承担企业责任 | 现阶段用个人认证验证算法；上线前转企业认证（见 [amap-key-application-checklist.md](amap-key-application-checklist.md) §2） |

## 4. 功能需求

### F1 路线输入（P0）

**用户故事**：US-01

**功能描述**：用户输入起点、终点与出发时间。

**详细规则**：

| 输入项 | 规则 |
| --- | --- |
| 起点 / 终点 | 支持文字搜索（地理编码）与地图点选；MVP 至少支持文字 + 地图点选之一 |
| **期望到达时段** | **必填**（v0.3 变更）。用户选一个时段，如 `17:00 – 20:00`。作用见 F6 —— 它是 F6 成立的前提 |
| 出发时间 | 选填。用于「预演某个具体时刻」的场景；若填了则以它为准，不再做优化 |
| 时间范围 | 限制在「当前时间 ~ 未来 7 天」。超出范围提示原因（太阳计算本身无限制，但天气数据与用户意图都在近未来） |
| 路线方案 | 若路由服务返回多条备选，展示前 3 条，用户可选 |

> **为什么「到达时段」是必填而「出发时间」只是选填**：
> 这是 M0 盲测的结论。用户的心智模型是「我要在某个时间到」，而「几点出发」正是产品要回答的问题。若把出发时间设为必填，产品就退化成一个被动计算器，还会因为缺少到达约束导致优化器选出「夜间出发」的无意义解（详见 [F6](PRD-sun-glare-route-planner.md) 与 [验证报告](m0-algorithm-validation-report.md) §3）。

**验收标准**：
- [ ] 输入有效起终点后 3 秒内开始请求路线
- [ ] **未填到达时段时，F6 不可用，并给出明确提示**（而非静默退化）
- [ ] 出发时间早于当前时间时给出警告但仍允许计算（用于复盘）
- [ ] 到达时段早于反推的出发时间（即时段太短、行程赶不上）时，给出可操作的错误提示
- [ ] 地理编码失败时给出可操作的错误提示，而非静默失败

### F2 路线获取与几何解析（P0）

**功能描述**：从路由服务获取路线的折线几何，并计算**每一段的行驶朝向（bearing）**。

**详细规则**：

| 项 | 规则 |
| --- | --- |
| 几何数据 | 需要每个路径点的经纬度，以及每段（leg/step）的朝向 |
| 朝向计算 | 优先使用路由服务直接返回的 `bearing`/`heading` 注解；缺失时用相邻两点的大圆方位角公式计算 |
| 分段粒度 | **100m**（可配置，见 6.4）。太粗丢失弯道细节，太细性能浪费 |
| 道路信息 | 尽量保留道路名称、编号，用于生成人类可读的清单（如「G42 沪蓉高速」） |
| 分段元数据 | 每段记录：`segmentId, startCoord, endCoord, headingDeg, distanceM, 累计里程, roadName` |

**验收标准**：
- [ ] 任取一条已知直线路段，计算出的 heading 与人工目测方向误差 ≤ 3°
- [ ] 路线总长度与路由服务返回值一致（误差 < 1%）
- [ ] 输入一条环形路线时不会出现除零或 NaN

### F3 逆光风险计算引擎（P0，核心）

**功能描述**：对路线上的每一段，在时间轴上逐点计算逆光风险分数。

**输入**：分段几何 + heading + 出发时间 + 路段行驶耗时（由限速或路由时长推算）
**输出**：每个 (segment, timestamp) 组合的 `offAxisAngle`（离轴角）与 `riskScore`（0–100）

**详细规则**：完整算法见 **第 6.3 节**。此处只列产品级要求：

| 要求 | 说明 |
| --- | --- |
| 风险分数 | 0–100 连续值，必须可解释（能拆解出各因子贡献） |
| 风险分级 | 低 / 中 / 高 / 极高 四档（阈值见 6.3.6） |
| 太阳不可见时段 | 太阳高度角 ≤ 0° 时，风险恒为 0（夜间/日出前/日落后） |
| 时间采样粒度 | **5 分钟**（可配置），避免出现「刚好错过」的假阴性 |
| 路段代表性 | 一个 100m 路段在时间轴上会有多个采样点，需聚合为单一分数（取 P80 分位或最大值，见 6.3.5） |
| 纯函数 | 计算引擎不得依赖网络与 DOM，便于单测与将来搬到 Worker/服务端 |

**验收标准**：

*(以下期望值已用参考实现数值验证，可直接作为单测锚点)*

| 用例 | 输入 | 期望输出 |
| --- | --- | --- |
| 太阳位置-春分 | 北京 (39.9042, 116.4074)，2025-03-20 12:00 CST | 方位角 ≈ **8.7°**（南偏东），高度角 ≈ **49.2°** |
| 太阳位置-真太阳时正午 | 同上，2025-03-20 **12:22** CST | 方位角 ≈ **0.2°**（正南），高度角 ≈ **49.5°** |
| 太阳位置-夜间 | 同上，2025-03-20 02:00 CST | 高度角 < 0° |
| 几何-正前 | heading=90°，A=90°，h=10° | θ = **10.0°**，R ≈ **56.7**（中）|
| 几何-正后 | heading=0°，A=180°，h=60° | θ = **120.0°**，R 为「低」|
| 几何-头顶 | 任意 heading，h=90° | θ = **90.0°**，R 为「低」|
| 几何-正侧方 | heading=0°，A=90°，h=0.5° | θ = **90.0°**，R 为「低」|
| 极端-日出直射 | h=3°，ΔA=0° | θ = 3.0°，R ≈ **89.8**（**极高**，守护动态范围）|
| 夜间归零 | 02:00 计算任意路线 | 全部路段 R = 0 |
| 单调性 | 固定 ΔA=0°，h 从 1° 递增到 60° | R **严格单调递减**（守护 6.4.2 的修订）|

> ⚠️ **实现陷阱提示**：北京的太阳正午是 **12:22 CST 而非 12:00**。原因是北京位于东经 116.41°，偏离 UTC+8 中央经线 120°E 约 3.59°（≈14.4 分钟），再叠加春分前后约 −8.3 分钟的时差方程。**若实现里得到 12:00 即正南，说明时区/经度处理有误。**

- [ ] 引擎单测覆盖率 ≥ 90%，且不依赖真实网络请求
- [ ] 6.4.6 校准表逐行复现（容差 ±0.2 分）
- [ ] 6.4.7 场景表逐行复现，且结论与「是否符合直觉」列一致

### F4 风险可视化（P0）

**用户故事**：US-01

**功能描述**：在地图上按风险等级为路线着色。

**详细规则**：

| 项 | 规则 |
| --- | --- |
| 着色方式 | 整条路线按段渲染，每段一个颜色 |
| 配色 | 低 `#4A90D9`（蓝）｜ 中 `#F5A623`（橙）｜ 高 `#E02020`（红）｜ 极高 `#8B0000`（深红）|
| 交互 | 点击任一路段，弹出该段详情：道路名、里程、时间窗、风险分数、离轴角 |
| 图例 | 常驻显示四级图例，含各级含义文字 |
| 无风险状态 | 全程低风险时，顶部显示**明确的绿色结论**：「本行程在所选时段内无逆光风险」，而不是给一张全蓝图让人自己猜 |
| 时段滑杆 | 提供时间滑杆，拖动即可看到该时刻的风险分布（P1） |

**验收标准**：
- [ ] 着色与数据一致，抽检 10 段颜色与风险等级匹配
- [ ] 移动端 375px 宽度下地图与详情可用
- [ ] 配色对红绿色盲用户可区分（不能只靠红/绿对立，需配合明度与图例文字）

### F5 高风险路段清单与时间窗（P0）

**用户故事**：US-02

**功能描述**：以列表形式给出需要关注的路段。

**详细规则**：

> 🟡 **v0.2 修订** —— M0 盲测发现「合并粒度」写错会直接毁掉清单可读性，已明确。详见 [验证报告](m0-algorithm-validation-report.md) §2。

| 项 | 规则 |
| --- | --- |
| 呈现内容 | 道路名 + 起止里程 + 时间窗 + 风险等级 + 一句话建议 |
| **聚合单位** | ⚠️ **必须按「道路名」聚合，不得按计算分段（100m）聚合**。计算分段是为精度选的，不是展示单元 |
| **为什么** | 实测：100m @ 53km/h = **6.8 秒**。按分段合并会产出 `07:00:26–07:00:32`、`07:00:39–07:00:58` 这种无法阅读的条目 —— 实测同一路线产出 15 条垃圾条目，按道路名聚合后降到 **3 条可用条目** |
| 相邻合并 | 同名道路的风险窗口若被短的非风险段打断，间隔 ≤ 60 秒应合并 |
| 排序 | 按峰值风险降序，同级按里程升序 |
| 时间窗 | 该段风险等级 ≥ 中的**时间区间**。例如 `07:02 – 07:05` |
| 案例文案（真实数据） | 「**东长安街**｜约 07:02–07:05 正对太阳（离轴角 0.4°）｜**高**｜峰值 67 分｜建议佩戴偏光墨镜」 |
| 空状态 | 无高风险时展示「全程安全」+ 最接近中风险的路段作为参考信息 |
| 时长标注 | 每个高风险段标注预计行驶时长与里程（帮助用户理解「要难受多久、多长」） |
| 道路名缺失 | 高德部分 `step` 的 `road` 为空（实测占比 0.9%），需 fallback 到 `instruction` 或「未命名路段」 |
| ⚠️ **瞬时路段** | 该路段本身过短（< 1 分钟行程）时，**标注为「瞬时」而非给出 `07:00–07:00` 的假区间**。实测：400m 路段 @ 53km/h 仅 27 秒 |

**验收标准**：
- [ ] 时间窗边界与地图染色在时间滑杆上一致
- [ ] **清单条目数应远小于计算分段数**：实测 1814 段 → 3 条清单。若条目数接近分段数，说明聚合失效
- [ ] **每条清单的时间窗宽度 ≥ 1 分钟**（不足 1 分钟的路段应标注为「瞬时」而非给一个假的时间窗）
- [ ] 清单条目点击后地图相应路段高亮并居中
- [ ] 道路名为空时不留空白，有 fallback 文案

### F6 建议出发时间（P0）

> 🔴 **v0.3 重大修订** —— 本节在 M0 真实数据盲测中被证明**原指标有概念性缺陷**，且新发现的**风险曲线不连续性**改变了整个交互设计。详见 [m0-algorithm-validation-report.md](m0-algorithm-validation-report.md) §3、§3.5。

**用户故事**：US-03

**功能描述**：用户选定**期望到达时段**，系统在满足该约束的可行出发时间中，找出逆光风险最低的方案，并明确标出**危险边界**。

**⚠️ 已废弃的原设计（保留备查）**：

```
原评分函数: 行程总逆光暴露度
          = Σ(每段风险分数 × 该段行驶时长) / 总行驶时长  + 峰值惩罚项
原搜索:     用户所选出发时间 ±3h，15 分钟步长
```

**为什么废弃** —— 实测：北京→天津 138.5km，用此指标扫描全天，**最优解是 19:00 出发**（太阳已落山，暴露度 0.0）。数学正确、产品无价值。

根因有两层：

1. **该路线 85% 东西向，但致命的只有 3.1km 西向路段**，在 18:16 迎上落日（太阳高度角 **0.04°**、离轴角 **0.00°**、峰值 **100.0 分**）。平均暴露度把 3.1km 的致命点 ÷ 138km 稀释掉了。
2. **更根本**：只要搜索窗口覆盖全天，优化器**必然**退化成「夜间出发」把风险压到 0。这不是路线问题，是**指标定义域问题**。

### F6 修订后的设计（v0.3）

#### 输入

| 输入项 | 类型 | 说明 |
| --- | --- | --- |
| **期望到达时段** | **必填**，如 `17:00 – 20:00` | **硬约束**。由行程时长反推可行出发区间。没有它，优化器必然选出夜间出发 |
| 最早可出发时间 | 选填 | 约束下界，如「我不想 6 点前出门」 |
| 路线与日期 | 沿用 F1 | |

> **行程时长是已知量**（高德返回 `duration`），所以「到达时段」可唯一映射为「出发区间」：
> `出发区间 = [arrive_from − duration, arrive_to − duration]`
> 用户不需要理解这一点，但实现上这是关键转换。

#### 主指标（替换平均暴露度）

| 优先级 | 指标 | 说明 |
| --- | --- | --- |
| **主排序键** | **峰值风险 $R_{max}(t)$** | 全路段最高分。**不再使用平均暴露度** |
| 并列展示 | 「高」以上等级的**里程占比** | 反映风险的空间广度 |
| 必须输出 | **峰值下界** $\min_t R_{max}(t)$ | 无论何时出发都躲不掉的最坏峰值，由路线几何决定 |

> **为什么平均暴露度是错的（可复用的教训）**：
> 平均类指标系统性**低估「局部致命」**。风险在本产品中是**空间聚集**的（几公里甚至几百米内致命），不是均匀分布的。用平均量描述聚集风险，必然丢失产品价值。

#### 🆕 搜索策略：必须处理风险曲线的**不连续性**

**这是本次盲测最重要的发现。** 峰值风险**不是**出发时间的平滑函数：

```
15:40  98.3   昆仑路   通过时太阳高度角  0.91°
15:45 100.0   昆仑路   通过时太阳高度角  0.04°   ← 死正对
16:00  99.5   金钟桥   通过时太阳高度角  0.46°
16:05  23.2   分钟寺桥 通过时太阳高度角 23.05°   ← 断崖，跳变 76.3 分
```

**机理**：一段致命的西向路在里程约 120km 处，行程需约 136 分钟。只有 **15:45–16:00 出发**，才会恰好在 18:16–18:18（太阳高度角 0.04°、离轴角 0.00°）通过它。16:05 出发则 18:21 才到，**太阳已落山，风险归零**。

**后果**：实测 15:00–17:30 区间内有 **15 个** 峰值 ≥ 60 的出发时刻，而 **15 分钟步长会漏掉其中 13 个**。

**因此搜索必须两阶段**：

| 阶段 | 步长 | 目的 |
| --- | --- | --- |
| ① 全局粗扫 | 15 分钟 | 覆盖全天，找候选区域 |
| ② 局部精扫 | **5 分钟**（或更细） | 在最优解附近与**所有等级跃迁边界**附近细化 |

**禁止**只做单步长全局扫描 —— 会漏掉窄窗口，且可能在尖峰边缘给出建议。

#### 🆕 输出：危险边界（比「最优时间」更有用）

实测数据里，正确建议**不是**「挑一个最优点」，而是：

> **16:05 之后出发，可完全避开该落日路段；16:00 出发则会在 18:16 正对太阳（离轴角 0.35°，峰值 99.5）。**

所以输出必须包含**危险窗口边界**：

| 输出项 | 说明 | 实测示例 |
| --- | --- | --- |
| **危险出发窗口** | 峰值 ≥ 60 的出发时间区间 | `15:05 – 16:00`（该区间出发会正对落日） |
| **安全出发窗口** | 峰值 < 60 的出发时间区间 | `16:05 – 17:30`、`07:15 – 15:00` |
| Top 3 推荐 | 在满足到达约束的候选中按峰值风险升序 | 见下 |
| **危险警告** | 若最优解距离危险窗口 < 15 分钟，**必须警告** | 「16:15 出发是安全的，但仅比危险窗口晚 15 分钟」 |

#### 评分与验收

| 项 | 规则 |
| --- | --- |
| 输出 | Top 3 建议时间，各自显示峰值风险、高以上里程占比、到达时刻、与用户原计划的改善幅度 |
| **反建议（强制）** | 当**可行区间内**的峰值下界 ≥ 60 时，**必须**输出「在您的到达时段约束下，本路线无法避开逆光」，并给出方位原因与应对建议（偏光镜 / 避开该时段 / 放宽到达约束） |
| 硬边界 | 不推荐凌晨出发（除非用户主动选择）；到达时段跨越日落时，需提示「部分行程将在日落后，无逆光风险但视线条件下降」 |

**验收标准**：
- [ ] 评分函数单调性：把某段风险调高后，峰值风险必须不降
- [ ] **到达时间约束必须生效**：给定「必须 18:00 前到达」时，不得推荐 19:00 出发

- [ ] **东西向长路线能正确给出「无法避开」的结论**（验收用例 T07）

## 6. 核心算法设计

> 这是整个产品的心脏。产品价值 = 这个算法的准确度。

### 6.1 问题形式化

给定：
- 路线分段集合 $S = \{s_1, s_2, \dots, s_n\}$，每段有起始点坐标 $p_i$、朝向 $\beta_i$（正北为 0°，顺时针）
- 出发时刻 $t_0$，每段的预计通过时刻 $t_i$（由累计里程与速度推算）

求：每段的风险分数 $R_i \in [0, 100]$

### 6.2 步骤一：太阳位置计算

对任意时刻 $t$ 与经纬度 $(\phi, \lambda)$，需要得到：

- **太阳方位角** $A$（从正北顺时针，0°–360°）
- **太阳高度角** $h$（地平线以上为正，单位度）

**实现要求**：
- 使用成熟的太阳位置算法（NOAA Solar Position Algorithm 或 SPA），不要手写简化公式
- 必须使用 IANA 时区正确处理 UTC 偏移与夏令时（中国无夏令时，但库要选对）
- 精度目标：方位角误差 < 0.5°，高度角误差 < 0.5°（远优于本产品 5° 的分级粒度）

**参考实现路线**：`suncalc` / `solar-calculator` 类库，或自行移植 NOAA 公式。**必须写单测锚定**（见 F3 验收标准）。

### 6.3 步骤二：离轴角（核心概念）

**定义**：**离轴角 θ** = 太阳方向与车辆前进方向之间的夹角。

- θ = 0°：太阳正对车头，最刺眼
- θ = 90°：太阳在正侧方，基本不影响
- θ = 180°：太阳在正后方，完全无影响

**关键区分**：产品关心的**不是**「太阳方位角与道路方位角的差」，而是三维空间中太阳方向与车头方向的实际夹角。因为太阳高挂时，即使方位对齐，光也是从上方来的，有遮阳板可用。

**计算公式**：

设 ΔA = |A − β| 归一化到 [0°, 180°]，则：

$$\cos\theta = \cos(h) \cdot \cos(\Delta A)$$

$$\theta = \arccos\big(\cos(h) \cdot \cos(\Delta A)\big)$$

**边界校验**（必须通过）：
- 太阳正前方地平线（ΔA=0, h=0）→ θ = 0°（最危险）✓
- 太阳正头顶（h=90°）→ θ = 90°（不刺眼）✓
- 太阳正后方（ΔA=180°）→ θ = 180°（无影响）✓
- 太阳正侧方地平线（ΔA=90°, h=0）→ θ = 90° ✓

### 6.4 步骤三：风险分数

$$R = 100 \cdot w_{angle}(\theta) \cdot f_{sun}(h) \cdot f_{weather} \cdot f_{shade} \cdot f_{terrain}$$

MVP 中 $f_{shade} = 1$（不做遮挡）、$f_{terrain} = 1$（不做坡度），$f_{weather}$ 见 F7，$f_{duration}$ 见 6.4.5（MVP 取 1）。

> **各因子的职责必须严格分离**，否则会出现 6.4.2 所述的量纲重复惩罚：
> $w_{angle}$ 管**几何方向**，$f_{sun}$ 管**大气衰减**，$f_{weather}$ 管**云层遮蔽**，$f_{shade}$ 管**地物遮挡**，$f_{terrain}$ 管**坡度**。同一个物理量不得进入两个因子。

#### 6.4.1 角度权重 $w_{angle}$

基于眩光的光学特性：偏离视线轴越远，眩光衰减越快。采用类 Holladay 的衰减形式：

$$w_{angle}(\theta) = \frac{1}{1 + (\theta / \theta_0)^{p}}, \quad \theta_0 = 15°,\ p = 1.6$$

| θ | 权重（精确值） | 含义 |
| --- | --- | --- |
| 0° | 1.000 | 正对，极端眩光 |
| 5° | 0.853 | 严重 |
| 10° | 0.657 | 严重 |
| 15° | 0.500 | 明显 |
| 20° | 0.387 | 明显 |
| 30° | 0.248 | 可感知 |
| 45° | 0.147 | 轻微 |
| 60° | 0.098 | 基本无感 |
| 90° | 0.054 | 无影响 |

**设计锚点**：$\theta_0 = 15°$ 使 $\theta = 15°$ 时权重恰为 0.5 —— 即「偏离 15° 时刺眼程度减半」。这与驾驶实际经验中「15° 以内是主要危险区」的认知一致。

> 说明：$\theta_0$ 与 $p$ 是**待调参数**（见 Q6/Q7），必须通过真实驾驶反馈校准。首版取上述经验值。$p = 1.6$ 表示衰减比 $1/\theta^2$（Holladay 眩光公式的经典形式）**稍缓和**，因为我们关心的是"主观不适"而非纯光学等效光幕亮度。

#### 6.4.2 太阳高度角因子 $f_{sun}(h)$

**重要设计说明（v0.1 修订）**：太阳高度角对眩光的几何影响**已经完整包含在离轴角 θ 中**（θ 由 h 与 ΔA 共同决定）。因此 $f_{sun}$ 不应重复施加几何惩罚，否则会导致两个问题：

1. **非单调**：正对太阳时分数会随 h 先升后降，出现「太阳稍微升高反而不那么刺眼」的荒谬结论
2. **死档**：分数上限被压到 80 以下，「极高」等级永不触发

$f_{sun}$ 只承担**残余物理修正** —— 低空太阳穿过更厚大气，散射更强（红移、光晕），主观不适略高。采用线性衰减：

$$f_{sun}(h) = \begin{cases} 0 & h \le 0° \\ \max\left(0.2,\ \min\left(1,\ 1 - 0.8\cdot\frac{h - 0.5°}{59.5°}\right)\right) & 0 < h < 60° \\ 0.2 & h \ge 60° \end{cases}$$

| h | f_sun | 说明 |
| --- | --- | --- |
| ≤ 0° | 0.000 | 太阳在地平线下，完全无光 |
| 0.5° | 1.000 | 刚出地平线，最强散射 |
| 5° | 0.939 | |
| 10° | 0.872 | |
| 20° | 0.738 | |
| 30° | 0.603 | |
| 45° | 0.402 | |
| ≥ 60° | 0.200 | 保底值，保证高挂太阳仍有残值（天顶散射光）|

**为什么用 0.5° 而非 0° 作为起始**：太阳视直径约 0.53°。以 0.5° 为「几何日出」，既避免 $h \to 0$ 处的取值争议，也留出 $\arctan$ 级的边界裕度。**$h \le 0$ 硬性归零**保证夜间计算绝对为 0。

#### 6.4.3 天气因子 $f_{weather}$

见 F7 表。阴天 0.25 意味着即使方向完全正对，最高也只有 25 分（低风险），符合现实。

#### 6.4.4 地形与坡度因子 $f_{terrain}$（v1.1）

有 DEM 高程后，用路段坡度 α 修正有效高度角：$h' = h - \alpha$（上坡时太阳相对更"高"，下坡时更"低"更危险）。

#### 6.4.5 持续时间因子（可选，用于疲劳累积）

长时间连续逆光会累积视觉疲劳。定义：

$$f_{duration} = 0.7 + 0.3 \cdot \min\left(1, \frac{T_{连续}}{30\text{min}}\right)$$

MVP 可先用 $f_{duration}=1$，v1.1 引入。

### 6.5 步骤四：时间采样与路段聚合

**问题**：100m 路段在时间轴上是区间，而非瞬时点。

**方案**：对每段 $s_i$，在其通过时间窗 $[t_i, t_i + \Delta t_i]$ 内按 5 分钟采样，得到若干 $\theta$ 与 $R$ 值。

**聚合规则**：

$$R_i = \text{percentile}_{80}\big(\{R(s_i, t_k)\}\big)$$

**为什么用 P80 而不是最大值或平均**：
- 用最大值 → 过度报警，路过一个瞬间就整段标红，用户会不信任
- 用平均值 → 漏报，一段里 1 分钟极端逆光会被 4 分钟正常冲淡
- P80 → 代表「这段路上你会明显感到不适的时间占比」，符合主观体验

**这条规则是产品可信度的关键，必须写进单测。**

> ⚠️ **v0.2 补充：P80 的已知局限（实测发现）**
>
> P80 会**抹平瞬时峰值**。实测：100m 路段 @ 53km/h 仅耗时 6.8 秒，而采样步长 5 分钟 → 该路段往往只有 1–2 个采样点；对于更长的路段，P80 会把「1 分钟的极端逆光」在「5 分钟的正常」中稀释。
>
> **这带来一个必须向用户诚实交代的结论**：
>
> | 量 | 能否靠改出发时间规避 |
> | --- | --- |
> | 路段级 P80 风险 | ✅ 能（优化器可压低它） |
> | 瞬时级峰值风险 | ❌ 可能不能（太阳就在那个方位） |
>
> 所以「建议出发时间」功能的天花板是：**能把路段级风险压下去，但压不掉瞬时峰值**。产品文案不得暗示「换个时间就没问题了」。
>
> **可能的改进方向（待验证）**：对路段内部也做细粒度时间采样（如 15 秒），并同时输出 `P80` 与 `max`，让用户看到「典型情况」与「最坏瞬间」两个量。当前 MVP 先保留 P80 作为分级依据，`max` 作为补充信息。

### 6.7 完整计算流程

```
输入：起点、终点、出发时间
  ↓
[1] 地理编码 → (lat, lon)
  ↓
[2] 路由服务 → 折线几何 + 每段 bearing + 道路名
  ↓
[3] 重采样为 100m 分段 → segment[]
  ↓
[4] 由限速/路由时长推算每段通过时刻 → t_i
  ↓
[5] 对每段、每 5min 采样点：
      a) 算太阳 (A, h)          ← 太阳位置库
      b) 算 ΔA = |A − β_i|
      c) 算 θ = arccos(cos h · cos ΔA)
      d) 算 R = 100 · w·f_sun·f_weather
  ↓
[6] P80 聚合成每段单一分数 R_i
  ↓
[7] 分级 + 地图着色 + 高风险清单 + 时间窗
  ↓
[8] 建议出发时间：重复 [4]–[6] 24 次（±3h，15min 步长），比较总暴露度
```

**性能提示**：步骤 [5] 是热点。可优化为：先算整条路线时间范围内的太阳方位角序列（与位置弱相关，可用路线中点近似，再对关键段精算），或把引擎放进 Web Worker / WASM。

### 7.2 双层数据源架构（应对约束 C1）

```
                    ┌─────────────────────────┐
                    │   RouteProvider 接口     │
                    │  getRoute(from,to,opts)  │
                    │   → RouteGeometry        │
                    └───────────┬─────────────┘
                                │
          ┌─────────────────────┼─────────────────────┐
          ▼                     ▼                     ▼
   OSRMProvider          ValhallaProvider      AmapProvider(预留)
   (MVP 默认, 免费)       (免费, 可自建)        (国内精度最佳, 需 Key)
```

**RouteGeometry 统一契约**（所有 Provider 必须返回）：

```ts
interface RouteSegment {
  index: number;
  start: { lat: number; lon: number };
  end: { lat: number; lon: number };
  headingDeg: number;      // 正北为 0，顺时针
  distanceM: number;
  roadName?: string;
  speedKmh?: number;
  source: 'osrm' | 'valhalla' | 'amap';
  confidence: 'high' | 'medium' | 'low';  // 数据置信度，透出到 UI
}
```

**这样设计的价值**：算法层完全不知道数据来自哪，切数据源不改一行算法代码。同时 `confidence` 字段让国内 OSM 数据不准的问题**对用户透明**，而不是悄悄算错。

## 附录 B：核心公式汇总

```
太阳位置：  (A, h) = SunPosition(lat, lon, utcTime)          [NOAA SPA]

方位差：    ΔA = normalize180(|A − heading|)

离轴角：    θ = arccos( cos(h) · cos(ΔA) )                   单位：度

角度权重：  w(θ) = 1 / (1 + (θ/15)^1.6)

太阳因子：  f_sun(h) = 0                              , h ≤ 0°
                      max(0.2, min(1, 1 − 0.8·(h−0.5)/59.5)) , 0 < h < 60°
                      0.2                            , h ≥ 60°

风险分数：  R = 100 × w(θ) × f_sun(h) × f_weather × f_shade × f_terrain

路段聚合：  R_segment = percentile80({ R(t_k) })

分级：      [0,30) 低 | [30,60) 中 | [60,80) 高 | [80,100] 极高

出发优化：  Cost(t) = Σ(R_i × duration_i)/Σduration_i + λ × max(R_i)
```

> **修订记录 v0.1**：$f_{sun}$ 原采用 $(\sin h)^{0.15} \times 1.2$ 并在 20° 处封顶，导致两个缺陷：
> ① 正对太阳时分数随 h **非单调**（h=3° 得 71.6，h=10° 反降到 60.6，h=30° 再降到 24.8）；
> ② 上限仅约 71.6，**「极高」等级永不触发**。
> 根因是太阳高度角对眩光的几何影响**已由 θ 完整承担**，$f_{sun}$ 不应重复施加几何惩罚。
> 已改为单调线性衰减，动态范围恢复为 0–100，且 h ≥ 20° 时正对也不超过「中」。
